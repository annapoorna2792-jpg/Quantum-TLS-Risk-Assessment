What the asymmetry costs

Two of three providers accept imported key material only under RSA wrapping. An adversary who records that exchange and later runs Shor's algorithm recovers the key, and everything encrypted under it.

Two constraints surfaced during the live import that are not in any reference architecture. The wrapping algorithm is not operator-selectable — AWS rejected RSA_AES_KEY_WRAP_SHA_256 for symmetric material, reserving it for RSA and ECC private keys. And BYOK requires kms:CreateKey, which cannot be scoped to a key ARN, so adopting customer-supplied keys widens the privilege footprint.

Threat model

Four adversaries. One is addressed and measured here; the others are named so the scope of the claim is unambiguous.

AdversaryCapabilityControlEvaluated
A1 · Passive network, future quantum Records import exchange and ciphertext; later obtains RSA private keys PQ import where available; nested envelope where not Measured
A2 · Compromised orchestrator Full control of middleware, credentials and key material in memory None in this prototype Unmitigated
A3 · Compromised or compelled provider Access to imported material at rest Nested envelope, partial — provider lacks Kpq Not evaluated
A4 · Stolen cloud credentials Legitimate-looking API access; needs no cryptographic capability IAM role scoping, instance credentials, audit trail Not evaluated
A4 is the most probable adversary in practice. A1 is the one this work addresses. That is a deliberate scoping decision — A1 is the adversary existing key management does not cover — but the system should not be read as secure against the threats institutions face most often.

The compensating control

Where a provider offers no post-quantum import channel, the data key is wrapped twice. The outer key never traverses that provider's channel — so a harvested import blob is insufficient rather than sufficient.

Outer — AES-256-GCM under Kpq
Key material crossed only a post-quantum-safe channel. Never sent to AWS or Azure.
Inner — provider key Kcloud
Imported under RSAES-OAEP. This is the layer Shor's algorithm defeats.
Data encryption key → ciphertext
AES-256-GCM, authenticated with tenant context.
Adversary is passive: it has recorded the import exchange and all ciphertext. Press run to grant it Shor's algorithm.
The 0% compromise rate is definitional — AES-256-GCM rejects decryption under an incorrect key. The contribution is the experimental design: key material is recovered in both conditions, which isolates which layer provides the protection. Without the single-layer baseline as a positive control, a working control could not be distinguished from a threat that was never realisable.
This does not make the provider's import channel quantum-safe, and it does not protect material at rest inside a compromised provider. Keys protected this way are recorded as hybrid_compensated, never pq_native.

Three posture values, kept strictly distinct in compliance reporting: pq_native — provider performed post-quantum import; hybrid_compensated — classical import plus the nested envelope; classical_only — no compensating control. Conflating the first two would misrepresent residual risk to an auditor.

Residual risk and scope

Stated rather than discovered.

Unmitigated

  • A compromised orchestration host defeats everything. Middleware holding plaintext key material is strictly worse than provider-managed keys, because it aggregates what providers would otherwise hold separately. Production requires wrapping inside an HSM boundary.
  • Key material already imported under classical wrapping cannot be retrospectively protected. It requires re-keying, and ciphertext produced under it stays exposed for its retention period.
  • KMS API endpoints are classically authenticated even where confidentiality is post-quantum protected.

Scope limits

  • The Google Cloud path was validated against a local RFC 9180 reference implementation, not the live service. The cryptography is real; interoperability is not claimed. Published HPKE test vectors were not run.
  • Saga providers are simulated. Fault injection at controlled rates cannot be performed against production services, and provider latency is not what was measured. Fault rates are a sensitivity range, not a prediction.
  • Benchmarks were taken on a burstable EC2 instance. The p50 interval spanned 0.3 µs across 200 samples, inconsistent with throttling during the run.
